## 2. 发布验收工具 `scripts/check_deployment.py`

对部署根执行 P5 §5 的强制发布检查；**任一强制项不满足即非零退出**。工具定义并钉死
manifest schema；对"演示过一次"**没有任何豁免开关**——P5 §6 逐字：
"两种完成标准不互相替代；'演示成功一次'不豁免 verified profile 的发布要求（落地方案 §9.2）"，
该提示随每个 real-loader 失败项与工具 help 原文输出。

### 2.1 用法

```bash
# 工作目录任意；相对路径一律相对 deployment_manifest.json 所在目录（部署根）解析
python scripts/check_deployment.py --manifest <部署根>/deployment_manifest.json \
    [--report <verdict 输出.json>]
```

- stdout：逐项 `[ok ]/[FAIL] check_id target —— 原因`，末行 `VERDICT=PASS|FAIL|MANIFEST_REJECTED`，
  随后为完整机器可读 JSON verdict（含逐项 check_id/target/ok/detail、counts、notice）。
- `--report PATH` 另存同一 JSON（可归档进验收记录）。
- 工具对被检树**只读**。

退出码：`0` 全部强制项通过；`2` manifest 不可信/不可用（不存在、非 JSON、schema 违例、
不安全路径、重复声明、**密钥类条目被拒**——拒绝即不再逐项检查）；`3` manifest 合法但存在
未满足的强制项。

### 2.2 强制检查项（任务 P5-02 a–e）

| 判据 | check_id | 内容 |
|---|---|---|
| a | `resource.exists` / `resource.sha256` | motion profile、每个资源、每个报告：相对路径文件存在 + 实算 SHA256 与清单一致（64 位小写 hex，拒绝占位值） |
| b | `report.pass` | `kind=profile_validation` 报告（calibrate.py validate/promote 形态）可解析为 JSON，且其**真实 schema** 的通过字段 `overall_pass`、`operator_reviewed` 严格为布尔 true（缺字段即失败），并完整核对八阶段通过与 physical 证据。判据与生产 `configs/motion_params.py::_check_report_binding` 消费的同源，**不发明字段** |
| c | `report.demo_acceptance` | `kind=demo_acceptance` 报告复用 `scripts/fit_grade_threshold.validate_demo_acceptance`（P4 §3.1 严格 schema + 四键）：任一未测 null → "不完整、不可验收"，直接判 FAIL（P4-T13 口径；对齐 `configs/demo_acceptance.json`） |
| d | `motion_profile.real_reload` | 对清单声明的 profile 调**生产 real loader** `load_motion_params(path, mode="real")`；任何异常即失败（verified 状态、全部运行期字段非 null、URDF/校准哈希、报告绑定与 parameter_sha256、各阶段 physical 证据等判据全部原样生效，工具不复制也不放宽） |
| e | （manifest 拒绝，退出 2） | 密钥不入哈希清单（P5 §5）：任何条目路径基名为 `secrets.json` 或以 `secrets.` 开头、路径段含 `secrets`、或 manifest 任一字符串出现 `configs/app_config.SECRET_KEYS` 键名（`dashscope_api_key`/`deepseek_api_key`）即拒绝整个清单。工具从不读取/哈希 secrets 文件内容 |
| 附加 | `report.reference` | 资源 `reports[]` 与 `motion_profile.verification_report` 的关联引用不得悬空；绑定报告 `kind` 必须为 `profile_validation` |
| 附加 | `report.binding_consistency` | manifest 声明的 `verification_report` 与 profile 内部 `verification.report_path` 归一后必须是同一文件（"对应报告"只允许一套真相） |

字段语义（本工具钉死的 schema，与 `scripts/check_deployment.py` docstring 同一份）：

- `provenance`：`"measured"`（缺省）或 `"simulated"`。这是**打包方自述的来源标记**，
  工具只回显进结论，绝不据此放宽或收紧任何判定；演示/联调用合成树必须显式标
  `"simulated"` 且不得进入实测证据目录（对齐 P5 §2）。工具不判定标记的真实性——
  真实性由 §3 现场记录与人工复核负责。
- 必需资源角色各声明一次：`urdf`、`motor_calibration`、`requirements`、`weights`、`class_map`、`camera_intrinsics`、`camera_extrinsic`、`app_config`、`vision_config`、`prompt`、`mock_config`、`sample_manifest`、`grade_samples`。资源文件未声明也会判 FAIL；旧的通用 `model_resource/config/camera_calibration` 角色不能代替这些角色。
- 必需报告类别各声明一次：`profile_validation`、`demo_acceptance`、`grade_threshold`、`vision_accuracy`、`footprint_validation`、`ripe_confusion`。另支持可选 `place_calibration`。
- `resources[].reports` 必须包含该角色的证据关联：URDF/电机校准→profile_validation；内外参→vision_accuracy；权重、vision_config、样本清单→三类视觉报告；class_map→vision_accuracy/ripe_confusion；grade_samples→grade_threshold。存在的报告不能只孤立列出。
- profile_validation 复用生产校验：顶层通过/人工复核字段严格为 true，八阶段集合齐全，每阶段 passed=true、checks 非空且全过、含通过的 physical 证据。空阶段或仅 mock/offline 证据均拒绝。
- grade_threshold 使用 K 拟合工具真实 schema：overall_pass/proposable 为 true、K 为有限正数，inputs.input_sha256 绑定 grade_samples。视觉报告须 overall_pass/operator_reviewed 严格为 true；demo_acceptance 复用四键校验。
- URDF/电机校准角色声明的路径必须与 profile 的实际资源引用一致；资源解析后不能越出部署根。
- `motion_profile.verification_report`：必须等于 profile 内部 `verification.report_path`
  归一后的同一文件（`report.binding_consistency`），且其 kind 为 `profile_validation`。

manifest 生成侧本清单**不提供自动生成器**：资源角色与关联报告是打包人的语义声明，
无法从目录树推导；手写模板 + 工具强制校验的分工见 P5-02 开发日志 §7（AD-P5-02-B）。

### 2.4 密钥规则（必读）

`configs/secrets.local.json` 与任何 secrets 文件**一律不进 manifest、不参与哈希**；
密钥由操作者现场填写到固定位置（P1 §3.1，`configs/app_config.SECRETS_LOCAL_PATH`）。
manifest 里出现 `secrets.json`/`secrets.*` 路径或密钥键名时工具整体拒绝（退出 2），
这是防止凭据被打包/分发/归档的护栏，不是缺陷。
