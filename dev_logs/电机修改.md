## 2. 修复的问题

### 2.1 基础指令码错误(指引 3.1,最高优先级)

`StsProtocol` 指令码按《飞特串行总线舵机通信协议手册》protocol_version=0 修正:

| 指令 | 旧值(错误) | 新值 |
|---|---|---|
| PING | 0x01 | 0x01(不变) |
| READ DATA | 0x04 | **0x02** |
| WRITE DATA | 0x05 | **0x03** |
| REG WRITE | 0x06(与 ACTION 混淆) | **0x04** |
| ACTION | 未独立定义 | **0x05** |
| SYNC WRITE | 0x83 | 0x83(不变) |

- 核对锚点:"读 ID 1、地址 56、长度 2"现在生成厂商示例帧
  `FF FF 01 04 02 38 02 BE`(旧版生成 `... 04 38 02 BC`)。
- 误导性封装 `reg_write_action()`(把 0x04/0x05 混成一条 0x06)与
  `reset_servo()`(型号相关、不可逆、本任务无需求)已删除,仅保留指令码常量
  并注释其用途边界;复位/EEPROM 操作不属于驱动职责。
- 帧头、ID、LENGTH、校验和、小端字节序、ERROR 位、广播无应答语义逐项复核,
  与手册一致。

### 2.2 写应答按设备实际配置,不按注释假设(指引 4.P0、Prompt §5.2)

- 新增 `StsProtocol.set_write_response() / write_expects_ack()`:每台舵机
  WRITE 是否等待状态帧由策略决定。
- `Sts3215MotorController.initialize()` 在任何 WRITE(含力矩)之前,逐台
  **读回** `Response_Status_Level`(vendor 表地址 8,纯 READ,不写 EEPROM):
  等级 0 = 全应答 → 等应答并校验 ERROR;等级 1 = 只回读 → WRITE 只承诺
  "整帧提交给串口";等级 2 连 READ 不应答,初始化直接以通信错误失败,不猜测。
- 应答策略未登记的单元(仅测试/离线直连路径)默认等待应答。
- 单播请求前 `flush` + 协议内部 pushback 清空,迟到应答不会被当作当前请求
  结果;`_recv_status` 逐字节扫帧头、校验 ID/长度/校验和。

### 2.3 整次时间预算落实到底层(指引 3.3)

旧版只在写前检查 deadline、串口无写超时,假总线 100ms 慢写在 15ms 预算下仍
返回成功;底层 `OSError` 裸漏。现在:

- `ByteTransport.write(data, timeout_s)` / `read(n, timeout_s)`:
  `timeout_s` 为**整次调用剩余预算**,协议层逐次传入。
- `SerialTransport`:打开 pyserial 即带有限 `write_timeout`(默认 0.1s 兜底),
  每次调用前把剩余预算写到 `write_timeout` / `timeout`(读阻塞分片
  = min(1ms 分片, 剩余预算));**不调用无界 `flush()`**;
  串口异常统一包成 `MotorCommunicationError` 并保留 `__cause__`,
  "设备未连接/已关闭"仍按 `MotorStateError` 分类。
- `_send()` 在阻塞写**返回后**再次检查 deadline:慢写即使最终写完也报超时,
  不返回成功;短写报通信错误。
- 错误分类:坏帧、短写、超时、总线错误、缺失反馈、部分读写 →
  `MotorCommunicationError`(保留原始原因);未连接、未使能力矩、设备报告的
  硬件故障 → `MotorStateError`;命令越限 → `MotorLimitError`。
- 运行期 I/O 重试次数保持 0,无"可选重试"生产路径。

### 2.4 连续反馈块读取(指引 3.6,保持本地数据语义)

- 新增 `_feedback_block_layout()`:从 vendor 寄存器定义推导块起止 ——
  STS3215 的 Present_Position(56)/Present_Velocity(58)/Present_Current(69)
  → 块 56..70 共 **15 字节**;不复制云端硬编码。
- `get_feedback()` 与 `CalibrationReader.read_snapshot()` 改为每台一次 READ、
  六台共 **6 次事务**(旧版 12 次);全部共用同一个绝对 deadline
  (`timing.read_timeout_s`),总时限不随台数倍增。
- 位置/速度/电流按块内偏移拆出:电流读 `Present_Current(69)`,
  `Present_Load(60)` 等中间字节透传但一律不解码(标定指南 4.3)。
- 任一失败整次失败:不返回部分数据或缓存、不递增 sequence、不重试;
  跨度超 `max_feedback_span_s` 判无效采样抛错;`sample_start_ns` /
  `sample_end_ns` 如实记录,age 语义仍以采样开始时间为基准。

### 2.5 指令完整预校验与单次同步提交(保持并补测试)

本地既有防护语义原样保留,并新增独立判别测试:

- 任何运动写入之前完成形状/类型/有限性/六个通道有效限位/换算/最终编码
  检查;NaN、Inf、任何关节或夹爪越限 → `MotorLimitError`,整条拒绝,
  **运动写入次数为 0**(含"最后一个关节/夹爪出错"用例);不静默裁剪。
- 有效限位继续用 `configs.motion_params.effective_joint_limits` 交集计算。
- 六个目标恰好一帧 SYNC WRITE,不等待到位;只承诺整帧提交,不承诺物理事务
  原子性或全部设备已执行。

### 2.6 线程模型与停止职责(不变更)

- 全部串口读写在当前调用线程顺序执行;无新增工作线程、后台 freeze、定时器
  或异步任务。
- 未移植云端 `emergency_stop()/_freeze_loop()/release_freeze()/wait_until_settled()`。
- `hold_current()` 恰一次有界读 + 恰一次同步写,返回所用反馈,返回后无后台
  活动;读失败不发送猜测的保持目标,写失败抛异常不伪报成功。
- 预算组合(文档已明确,未新增配置字段):读段 ≤ `timing.read_timeout_s`、
  写段 ≤ `timing.write_timeout_s`,最坏合计两者之和。
- 故障锁存、`reset_fault`、到位等待继续由上层负责;初始化不做隐藏回零、
  恢复出厂或 EEPROM 写入。

### 2.7 换算模型(零改动,回归确认)

严格遵守《真机参数测量与标定指南》4.2/4.3/4.4:`mid=(range_min+range_max)/2`、
`360/(resolution-1)` 归一化、`round()` 取整、电流
`(decoded_raw_current - current_zero_raw) * current_ma_per_raw`、姿态速度乘
`joints.sign`、夹爪 %/s 与端点百分比公式、open_raw<closed_raw 支持、
零分母与越界观测抛错。homing_offset 只登记不使用;第 12 节四个共享函数
`bus_deg_to_urdf_deg / urdf_deg_to_bus_deg / raw_to_gripper_pct /
gripper_pct_to_raw` 签名与行为不变。

## 3. 接口兼容性(Prompt §四)

- 使用本地 `configs/common_interface.py` 导出的 `FloatArray`、`JointFeedback`
  与异常类,未复制第二套同名类型。
- `send_action / get_feedback / hold_current` 三方法签名不变;`JointFeedback`
  返回全部 9 个原有字段,关节顺序保持本地 `JOINT_NAMES`/`MOTOR_NAMES`
  (姿态 ID 1–5、夹爪 ID 6),未改成云端三个 `(6,)` 数组。
- `Sts3215MotorController` 构造调用方式与生命周期方法
  (`initialize/configure_torque/read_torque_enabled/close/__enter__/__exit__`)
  保持;`MotorMapping`、`CalibrationReader`、共享换算函数、`load_motor_calibration`
  的导入路径与行为契约不变;`CalibrationReader` 快照键集合与时间戳语义不变。
- 唯一对外可见的内部接口变化:`ByteTransport.write/read` 增加可选参数
  `timeout_s`(默认 None)。此处为勘误(FINAL-P3-005):原表述"向后兼容,
  不影响任何调用方代码"只对**调用方**成立(协议层是唯一调用方,已同步
  更新);对**实现方**是破坏性契约变更——协议层现在以关键字传
  `timeout_s=...`,只实现旧签名 `write(data)` / `read(n)` 的注入对象在第
  一条命令即抛 `TypeError`(被 `_send` 包装为 `MotorCommunicationError`,
  `__cause__` 保留,失败模式可诊断)。新契约要求实现方接受 `timeout_s`
  并落实有限阻塞时限。`ByteTransport` 是驱动内部测试缝而非冻结公共接口
  (`common_interface.py` 未包含它);仓内全部实现(`SerialTransport`、
  `FakeBus`、`test_calibration` 替身)均已更新,无旧签名实现残留。外部
  自定义 transport 若需兼容旧签名,需在协议层另行做能力检测回退(本轮
  未实现,按新契约成文)。
- 未修改任何规范文件使代码"显得合规";未发现本地接口与开发文档之间存在
  阻塞性冲突。
