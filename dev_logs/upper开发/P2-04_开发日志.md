## 2. 实现说明

### 2.1 `requirements.txt` 新节（`# --- P2 语音与云模型 ---`）

放在"真机 STS3215 串口驱动"之后、"开发期测试"之前——沿用文件既有形态
（`# --- 分组名（规格出处） ---` + 条目上方多行中文注释；`pyserial` 一节就是
"惰性导入 + 未安装也能 import"的同族先例）。节内注释分四层，顺序固定：

1. **节头说明**：用途（录音 + VAD + 两家显式 REST）；**惰性导入事实**——
   `qingyun/asr.py`/`qingyun/cloud_model.py` 顶层只有 `__future__`/`typing`，四个包
   一律在 `init()` 之后的私有工厂内经 `__import__` 动态载入，import 零副作用；
   由此得出"**运动与离线测试在缺少本节全部包的环境下也能全绿**"（P2-01/02/03 全程
   注入替身），只有真实麦克风/真实账号烟雾（P5）才需要它们。
2. **状态表**（"增补条目 ≠ 已安装 ≠ 已验证"）：httpx 0.28.1 开发机已装并验证；
   sounddevice / silero-vad / onnxruntime / torch 开发机**未安装**（import 即
   `ModuleNotFoundError`）；torch 不单独钉条目的理由就地写明。并明确一个**容易被高估
   的口径**：缺包时代码路径是抛 HardError，但 pytest 把默认工厂全部 monkeypatch 掉了，
   该分支**没有被任何测试执行过**——属代码阅读证据，不是测试结果（§3 附手工探针）。
3. **弱证据层**：`pip install --dry-run -r requirements.txt` 的解析结果与它**能说明/
   不能说明**什么（只说明约束互不冲突；不说明 arm64 轮子可得、装得上、麦克风能用、
   VAD 精度达标）。
4. **边界声明**：P3 视觉依赖（相机 SDK/OpenCV/YOLO 推理栈）不在本期条目内，归队友与
   P3 交付，避免本阶段提前绑定与 silero 冲突的 torch/onnxruntime 组合。

四条条目与约束理由（逐条都在其上方注释里写明验证状态）：

| 条目 | 约束 | 依据与状态 |
|---|---|---|
| `httpx` | `>=0.28,<0.29` | 两处 `_new_http_client` 显式 `HTTPTransport(retries=0, http2=False)` + `follow_redirects=False`（P2 §3.2/§4），禁 SDK 隐式重试属**代码层**约定；上限 <0.29 的另一理由是 P2-T19 白盒断言读了 `client._transport._pool._retries` 这类私有属性。开发机 0.28.1 已装，且 T17/T19 用**真实 transport + 127.0.0.1 服务子进程**做过 wire 级验证 → 唯一"已验证"条目；目标机仍须复验。 |
| `sounddevice` | `>=0.4.6,<0.6` | 录音输入（`_open_input_stream`/`_enumerate_input_devices`，P2 §3 阻塞按块读取）。PortAudio 系统依赖：dry-run 解析到 0.5.6 的 `py3-none-any` 纯 Python 轮子（cffi 绑定）→ Linux 上 PortAudio 由系统提供（`apt install libportaudio2`，自编译还需 `portaudio19-dev`）。**开发机未安装、未验证**；目标机不可用时按 §3 换等价库、封装在私有工厂内、公开签名不变。 |
| `silero-vad` | `>=4.5,<6` | VAD 运行时（`_load_vad` 优先 `load_silero_vad(onnx=True)`、回退 `onnx=False`；帧长 512@16k、阈值官方默认）。下限 4.5 只是"该版本线起提供 `load_silero_vad` 入口"的**保守估计且未验证**；上限 <6 防官方 6.x API 变更。注释登记两条 P5 锁定项：①该包把 torch 列为依赖（dry-run：silero-vad 5.1.2 → `torch>=1.12.0` 解析到 torch 2.14.0 + torchaudio 2.11.0 + 一批 nvidia-*/cuda-*），而 `_SileroVad.probability` 逐帧以 `torch.FloatTensor` 作输入容器，**ONNX 与 torch 两条路径都实际拉进 torch**，arm64 宜 CPU-only 轮子；②numpy 共存只在 x86_64 解析层成立。 |
| `onnxruntime` | `>=1.16,<1.20` | VAD 首选后端（onnx=True 分支），只经官方入口间接使用，本模块不自建 `InferenceSession`、不臆造状态张量形状。dry-run 解析到 1.19.2 的 `cp310-manylinux_2_27/2_28_x86_64` 轮子；arm64 tag、glibc/torch 搭配、512 帧实测延迟均**待验证**。**开发机未安装、未验证**。 |

### 2.2 `configs/app.json` / `configs/app.mock.json` 字段核对（方法 + 结论）

核对采用"三方逐字比对"：模板 JSON ↔ P1 §3.1 文档 JSON 块 ↔ `load_app_config` 的
必填键集合 ↔ `asr._validate_asr_settings` / `cloud_model._validate_llm_settings` 的
消费字段。**结论：完全一致，两个模板都无需改动。**

| 位置 | 模板键 | P1 §3.1 文档 | `app_config` 校验集合 | init 消费 |
|---|---|---|---|---|
| 顶层 | `profile_path`/`vision_config_path`/`prompt_path`/`log_dir`/`asr`/`llm` | 一致（`_note` 类额外键会触发"未知键拒绝"） | `_require_object(expected)` 同集合；mock 入口再并 `mock` | 路径四字段 → 绝对 Path；`prompt_path` 由 `cloud_model.init` 读一次 |
| `asr` | `model`/`endpoint`/`cloud_total_timeout_s` | 逐字相等 | `{"model","endpoint","cloud_total_timeout_s"}` | `_validate_asr_settings` 三字段（拒绝占位模型名、要求 https 完整 URL、要求有限正数） |
| `llm` | `model`/`base_url`/`total_timeout_s` | 逐字相等 | `{"model","base_url","total_timeout_s"}` | `_validate_llm_settings` 三字段（请求地址 `base_url.rstrip('/')+'/chat/completions'`） |
| `mock`（仅 mock 模板） | `asr_script_path`/`vision_replay_dir` | P1 §3.1/MockSettings | `{"asr_script_path","vision_replay_dir"}`；production 出现 mock 段即拒 | 只被 `scripts/run_mock.py` 读，不进气实配置 |

取值层面的实质一致性（D20/D12）：`asr.model == "qwen-audio-3.1-asr-flash"`、
`asr.endpoint == "https://dashscope.aliyuncs.com/api/v1/services/aigc/multimodal-generation/generation"`
（= P2 §3.1 写明的北京默认 endpoint，且文档里出现该串）、`cloud_total_timeout_s == 30.0`、
`llm.model == "deepseek-flash"`、`llm.base_url == "https://api.deepseek.com"`（= P2 §4
默认）、`total_timeout_s == 30.0`。超时数值按 P1 §3.1 末段属"建议默认，目标机实测后由
P5 锁定"，本任务不动。

**关于 `app.mock.json` 的 `"mock"` 模型名**：该值是模板占位，生产 `init` 会拒绝
（`_PLACEHOLDER_MODEL_NAMES` 15 项含 `mock`/`mock-model`/`placeholder`/… ，比对前
`strip().lower()`），而独立 mock 入口**不调用** `asr.init`/`cloud_model.init`（D15），
故不构成冲突——这条"为什么允许"的说明已经存在于三个地方（`asr.py` 第 89–91 行与
`cloud_model.py` 第 89–91 行的常量注释、P1 §3.1 末段、P2 §2 的 mock 说明段）。
JSON 没有注释语法，而**任何**注释型键都会被拒（§3 附拒绝实验），所以模板内不加、也
加不了说明；`configs/app.json` 与 `configs/app.mock.json` 均**保持原样**。

## 5. 问题与限制

1. **四条依赖里只有一条算"已验证"**（httpx 0.28.1，wire 级）；sounddevice/silero-vad/
   onnxruntime（以及被带入的 torch）在本开发机**完全未安装**，因此它们的功能性
   （真实设备能力、VAD 概率与 0.5 阈值是否够用、512 帧延迟、ONNX 权重下载与加载）
   **一条都没被证明**。requirements 里的约束是"可解析 + 与运动学不冲突"级别的证据。
2. `silero-vad>=4.5` 的下限是**保守估计**（按"`load_silero_vad` 入口存在于该版本线"
   推断），未在开发机验证；若目标机解析到的版本不含该入口，`_load_vad` 会抛
   ASRHardError（fail-fast，不会静默降级），届时收窄下限即可。
3. dry-run 的 numpy 共存结论**只在 x86_64 解析层成立**，且 pip 只解析了元数据；
   真正 `pip install` 后 `import torch`/`import onnxruntime` 是否与 placo/pin 的
   cmeel 二进制共存，尚未测过（arm64 亦然）。
4. arm64 侧未知项集中且量大：PortAudio 系统库与设备枚举、sounddevice 是否需自编译、
   onnxruntime/torch 的 aarch64 轮子与 glibc 组合、torch 该走 PyTorch CPU 索引还是
   conda-forge、VAD 权重随包分发还是需下载（P2 未规定，需 P5 决定并归档）。
5. **未解决冲突风险（跨阶段）**：P3 视觉栈很可能自带另一套 torch/onnxruntime 版本要求；
   本期刻意把视觉依赖排除在 requirements 之外，但**同一 conda env 里两套 torch 版本
   要求最终必须调和**（P2 §3 的"与视觉栈依赖解耦"只做到了代码层不 import，环境层仍
   会相撞）。这是留给 P3/P5 的复审项，不是本期能关闭的问题。
6. `configs/app.json` 的 `vision_config_path` 指向 `configs/vision.local.json`，该文件
   **仓库内不存在**（本地/P3 交付，属 P3 init 与预检第 4 条的范围）；`profile_path`
   指向的 `calibration/REAL_ARM/PC/profile.json` 存在并由既有模板用例断言 is_file()，
   `prompt_path` 指向仓库根 `prompt.md` 亦存在。既有测试只查后两个仓库内资源，
   故本期核对只到"字段与结构逐字一致"，不替 P3 断言 vision 配置内容；两个字段未动。
7. 超时数值（30.0/30.0）沿用 P1 §3.1 的"建议默认"，P2 §3.1/§4 要求它们经目标机
   实测后由 P5 锁定；本期不改，也不声明其合理性。
8. 本任务不引入新测试（任务书禁止改测试），因此"requirements 内容与代码注释一致性"
   这类事实**没有**自动化守护，靠 §7 的登记与人工审查维持。

## 7. 自主决策

- **DEC-P2-04-A（登记 4 条、不登记 torch 条目）**：规格 §2 只点名三样
  （sounddevice、silero VAD 运行时、httpx），而实现里 `_load_vad` 用
  `silero_vad.load_silero_vad`、`_SileroVad.probability` 用 `torch.FloatTensor`、
  onnx 分支由 `onnxruntime` 承载。候选①"把 torch 也写成显式条目并钉版本"——**否决**：
  开发机对 torch 一个版本都没装过、没验证过，钉版本等于把臆定写进锁定文件，且 arm64
  该走 PyTorch CPU 索引/conda-forge 属部署决策（P5），钉死反而挡路。取②：登记
  `onnxruntime`（它是 §3 点名的"首选运行时"）与 `silero-vad`，torch 由其依赖解析带入，
  并在注释里把"两条路径实际都需要 torch"写明——**不隐瞒、不假装已锁**。
- **DEC-P2-04-B（区间用"可解释的宽松"，且逐条写理由）**：`>=x,<y` 的每个上限都给的是
  **具体失效模式**而不是玄学保守：httpx `<0.29`（白盒私有属性 + Transport 形态）、
  sounddevice `<0.6`（PortAudio 绑定形态变更风险线）、silero-vad `<6`（官方 6.x API
  变更）、onnxruntime `<1.20`（开发机解析恰落在该线以内、x86_64 有实测轮子）。
  同时明确否决任务书点名的两个错误做法：为"本机装不上"而省略/注释掉依赖、把未验证
  版本写成"已验证"。**未**用 `--no-deps` 或环境标记（`platform_machine=='aarch64'`）
  做条件安装：本期 P2 测试在无这些包的环境下也必须全绿，条件标记会把"目标机才装"
  的意图藏进语法里，注释比标记更可审查。
- **DEC-P2-04-C（把"验证"拆成三个可分辨的层级写进注释）**：①已安装并验证（httpx，
  且验证方式是 wire 级本地服务而非替身）；②dry-run 解析证据（版本/tag，明确标注
  "不构成安装或运行验证"）；③未安装未验证（其余全部，附"缺包 → HardError 分支未被
  pytest 执行"的口径修正）。之所以做到这个粒度：把"解析成功"写成"验证通过"是本类
  收尾任务最典型的造假路径，而把"代码写了 fail-fast"写成"测试证明了 fail-fast"是
  第二典型的——两条都在此处显式分开。
- **DEC-P2-04-D（app.mock.json 不加任何形式的注释，说明留在代码与文档）**：JSON 无
  注释语法；可尝试的"合法变体"（`_note`/`_comment` 键、把说明塞进某个字符串值）要么被
  `load_app_config` 的**未知键拒绝**直接打红（§3 实验：顶层与 `asr` 段各一次），要么
  污染真实消费值（`asr.model` 会被 `cloud_model`/`asr` 当模型名发出去）。取：模板一字
  不动，"mock 占位名会被生产 init 拒绝、而 D15 的 mock 入口不调 init"这层因果写在
  已有位置（两个模块的 `_PLACEHOLDER_MODEL_NAMES` 常量注释 + P1 §3.1 末段 + P2 §2 的
  mock 说明段），本日志 §2.2 汇总索引。附带核对：`configs/app.json` 与 P1 §3.1 的
  JSON 块**逐字相等**（比对脚本按顶层/asr/llm 三段分别判等，全 True）→ 无缺漏、无多余，
  故模板**未改**（任务书条件"仅当发现缺漏才改"未触发）。
- **DEC-P2-04-E（回归顺序与耗时如实登记，不做"为省时间的裁剪"）**：P2 §6 步骤 5 的
  两条命令都跑（定向 248 → 全量 966/0），另加一条配置面定向（203 passed）作为模板核对
  的常驻锚点；未把耗时 10 分钟的全量改成子集"代表"结果（沿用 DEC-001 的耗时口径登记）。
  改动前与改动后两次全量都记录在案，并在 §3 显式说明**最后一次纯注释改写**与后一次
  全量的先后关系及其不可影响性论证——收尾任务里"我改了一行注释所以结果仍然有效"这种
  话要么不写，要写就得给出可核查的理由（requirements.txt 不被任何测试读取）。
