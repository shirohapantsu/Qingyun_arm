## 2. 实现说明（文件 + 关键符号）

### 2.1 `qingyun/grabbing/arm_control.py`

- **`@dataclass(frozen=True) class MotionTraceEvent`**：字段
  `sequence:int, time_ns:int, stage:str, kind:str, outcome:str|None`，逐字对应规格；冻结因此
  可哈希，工具侧可安全去重/做 dict 键。
- **kind 词表**（模块常量）：`TRACE_STAGE_ENTER="stage_enter"`、
  `TRACE_DESCENT_SUBMIT="descent_submit"`、`TRACE_FAILURE="failure"`、
  `TRACE_RESULT="result"`；三态 outcome 常量 `DESCENT_SUBMITTED/REJECTED/UNKNOWN` 定义在
  executor 侧（两层共用一份，运动层不重复写字面量），并由 `TRACE_DESCENT_OUTCOMES`
  随事件类型在控制层再导出，供 P4-03 的工具与测试引用。
- **`ALL_STAGES`**：文档 6.3 状态表的 14 个阶段名，事件上限按它封顶（`len+3=17`）。
- **`_MotionTraceCollector`（内部类，不公开）**：`clock_ns` 由控制器注入的时间源构造；
  `begin_call/snapshot/note_stage/note_failure/note_result/watches_descent/
  note_descent_submit`。有界性由三件事保证：stage_enter 每阶段名一次（`_entered` 集合）、
  descent_submit 一次（`_descent_done`）、failure 一次（`_failure_done`）、result 一次
  （`note_result` 顺手 `_armed=False`，此后一切写入空操作）。事件列表是普通 list，
  `snapshot()` 每次新建 tuple，内部列表不外泄。
- **武装门**：只有 `grasp_and_place` 期间 `_armed=True`。`move_joints/open_gripper/
  close_gripper/reset_fault` 等公开路径同样经 `_set_stage` 改写阶段，但未武装时只是裸赋值，
  因此**不会污染上一次调用交出的快照**（规格："返回后保留到下一次调用"）。
- **`get_last_motion_trace()`（公开）**：trace 关闭时返回 `()`；否则返回内部列表的 tuple 快照。
- **开关形态**：`ArmController(..., enable_motion_trace: bool = True)` 关键字参数。
  False 时**根本不构造收集器**（`self._motion_trace is None`）且给执行器传 `None`，
  所以关闭态没有事件列表、没有额外分支判断，逐字节等于加 trace 之前的运动路径。
- **`_set_stage` 是 `_stage` 改写的唯一入口**：原 13 处 `self._stage = X` 全部改为
  `self._set_stage(X)`（技能入口 12 处 + 公开原语/reset_fault），先赋值再记事件。
- **`failure` 的位置**：`_fault_result` 内顺序为 `_latch()` → `_note_failure(status)` →
  `executor.hold_position()` → `_set_stage(FAULT_*)` → 构造 GraspResult。即 failure 事件在
  保持提交与阶段改写**之前**，`stage` 字段是原始阶段（DESCEND/CLOSE/…），`outcome` 是原始
  status；随后 `stage_enter FAULT_HOLD` 另记一条，快照因此同时留下"原始阶段/最终阶段"。
  `_early_fail` 的"臂未动"分支同样记一条 failure（stage=CHECK，阶段不被改写）。
  `_refuse`（入参/配置拒绝）只记 result、不记 failure——它不是运动失败，`began_descend`
  一类推导不受影响（自主决策，见 §7）。
- **`result` 的位置**：四个 GraspResult 构造点（`_refuse/_result/_early_fail/_fault_result`）
  统一经 `_note_result(result)` 记录，原样返回**同一个对象**，因此"每调用恰好一条结果、
  outcome=最终 status"不依赖调用点写法，也不改任何字段。
- **不新增时间源**：收集器只用 `ArmController.__init__` 收到的 `clock_ns`（与执行器同一个），
  仿真侧即 `SimTime.monotonic_ns()`（纯读，不推进 `now_s`）。

### 2.2 `qingyun/grabbing/executor.py`

- **`MotionTraceSink`（Protocol）**：`watches_descent() -> bool` 与
  `note_descent_submit(outcome: str) -> None` 两个方法。执行器不认识阶段名、不构造事件、
  不持有事件列表，只在该上报时把事实交给上层；标定工具也不通过本协议碰控制器内部。
- **`SyncExecutor(..., motion_trace: MotionTraceSink | None = None)`**：构造注入。
  `play_segment` 的签名**不变**（现有测试用一元 lambda 包装它，签名一变就会炸）。
- **`first_descent_node_index(segment) -> int | None`（"非零下降节点"判定口径）**：
  1. 笛卡尔段以 `tcp_targets[k][2,3]`（该节点命令的基座 Z）为准，基准是**段起点节点 0**，
     取首个满足 `z0 - z_k > 1e-9 m` 的节点。节点 0 自身位移为零，永不入选；
  2. 因此"起点已在目标高度"的段（轨迹层按零位移只出一个节点，`nodes <= 1`）没有下降节点，
     返回 None——不为它伪造 submitted；
  3. 幅值阈值 1e-9 m 与轨迹层零位移判定同源（`trajectory._ZERO_DISPLACEMENT_M` 是私有常量，
     不 import 私有名，此处同值并注明出处）。由于终点相对起点的累计降幅等于全长，任何真实
     下降段必然存在这样的节点（最迟是最后一个节点），所以"找不到"只发生在零位移段与竖直向上段；
  4. 符号：`dz > 0` 的竖直向上段全部节点在基准之上 → None（下降段绝不允许用上升指令冒充
     "已开始下发下降指令"）；
  5. 兜底：段没有 `tcp_targets`（关节段）时退化为"相对节点 0 关节角变化首次超过 1e-9 deg 的
     节点"。控制层的 DESCEND 只由竖直笛卡尔段构造，兜底分支不会在正常抓取链上被用到。
- **上报点与三态**：`play_segment` 在段首问一次 `watches_descent()`，需要观察才做一次纯计算的
  `first_descent_node_index`；循环内只有 `k == descent_node` 那一条走
  `_submit_descent_node()`：`self.submit(...)` 正常返回 → `submitted`；抛异常 → 先
  `classify_descent_submit_error(exc)` 记 `rejected`/`unknown` 再**原样 raise**。
  提交次数、发送时机、读回次数与不接钩子时完全一致。
- **`classify_descent_submit_error(exc)`（三分法）**：`MotorLimitError`（含执行器翻译成
  `ExecutionError("PLAN_INVALID")` 的 cause 链）= 驱动写入前整条拒绝 → `rejected`；
  `MotorCommunicationError`、`MotorStateError`、未被翻译的异常、`KeyboardInterrupt` 等一切
  不能证明是否已落笔的情形 → `unknown`。规格只承认"明确写前拒绝"这一种非成功的可证明否定，
  所以 `MotorStateError`（设备未就绪，可能已有半帧落总线）也保守判 unknown——宁可交给操作者
  补证，也不把"不确定"折算成 False/没发过。
- 观察条件是 `armed and not descent_done and current_stage == DESCEND`，因此：预规划、
  APPROACH、以及 DESCEND 段首个非零下降节点**之前**的失败（例如零位移起点节点被拒、段内
  读回超时、发送前步长复查失败）都不会产生任何 `descent_submit` 事件。

## 5. 问题与限制

- **本任务只交付 trace 与不变性证据，不交付 JSONL 导出**：`began_descend`/
  `descent_evidence` 字段、`record_pick_place_trials.py` 与 `calibrate.py` 的 hardware
  pick_place 校验属 P4-03。本文件里的 `began_descend_of()` 只是**测试侧镜像**，用来钉住
  §2.8.2 的推导口径（submitted→True、rejected/无事件→False、unknown→null），不是工具实现。
- **"首个非零下降节点"用累计降幅判定，不用相邻差分**：起点已在目标高度的段只出一个零位移
  节点，此时没有下降节点，trace 里就没有 `descent_submit` 事件，工具按"无事件=False"登记。
  这在物理上是对的（确实一条下降指令都没下发过），但如果将来出现"下降段被拆成多段"的规划，
  观察条件仍只匹配 stage==DESCEND 且每次调用只记第一条，语义仍是"首次下降发送"。
- **1e-9 m 阈值的边界**：与轨迹层零位移判定同值。相对起点降幅不超过 1e-9 m 的节点不计为下降；
  由于终点降幅等于全长，任何真实下降段必然命中该判定（最迟在最后一个节点），因此不存在
  "真实下降但记不出边界"的空档。若未来允许亚纳米级下降指令，需要重新审视该阈值与
  `trajectory` 的零位移常量（两边必须同步）。
- **`unknown` 的保守性**：`MotorStateError` 也判 unknown（不是 rejected）。理论上"设备未就绪"
  多半没落笔，但规格只承认"明确写前拒绝"，无法证明的就不给 False。
- **不改 `_refuse` 的语义**：入参/配置拒绝不产生 failure 事件（只有 stage_enter+result）。
  若 P4-03 希望"拒绝也记 failure"，只需在 `_refuse` 里加一行 `_note_failure`，但当前
  `began_descend` 与分母推导都不依赖它，故不加，避免把"臂未动的入参错误"与运动失败混同。
- **异常逃出 `grasp_and_place` 的路径**（理论上不该存在，契约是任何失败都返回 GraspResult）：
  此时不会有 result 事件，快照保留到失败点，下一次调用 `begin_call` 清空。trace 因此可能
  "缺一条 result"，工具按 §2.8.3"导出完整性验证拒绝无法确定分母的试验"处理，不得补伪造事件。
- 运动回归耗时：一次完整抓取约 10~25 秒 CPU 时间，`test_motion_trace.py` 全量约 223s；
  新增 3 条 `test_grasp_flow` 用例仅 9.7s（刻意选用零指令/一条指令的廉价场景，昂贵场景的
  开关不变性由 `test_motion_trace.py` §7 承担）。

## 7. 自主决策

1. **开关形态 = 构造参数 `enable_motion_trace: bool = True`（默认开）**。理由：(a) 规格把
   trace 定义成 §2.8.2 里标定工具依赖的常规证据链，默认关闭会让工具必须知道特殊装配；
   (b) 关闭时 `self._motion_trace = None` 且执行器拿到 None，是"零收集、零占用"最彻底的形态
   （运行中再切换会留下一个已被创建但空着的列表，或需要每 tick 判开关，二者都比"构造期决定"
   更弱）；(c) 不动 `main.py`/`run_mock.py` 的构造。暴露 `motion_trace_enabled` 只读属性供
   工具与测试核对。
2. **钩子接线 = 构造注入 `MotionTraceSink` 协议，`play_segment` 签名不变**。任务书给了两种
   建议（play_segment 接受可选 trace 上下文 / executor 构造注入 recorder），选后者：
   `tests/test_grasp_flow.py` 既有用例把 `arm.executor.play_segment` 换成**一元 lambda**
   （`test_段起点偏差时重新规划到同一目标` 等），加参数就会破坏既有用例——而"不改既有用例"
   是本次硬约束。协议注入同时让执行器不认识阶段名（阶段判断留在收集器的
   `watches_descent()`），依赖方向仍然是 arm_control → executor，无环。
3. **"非零下降"判定的具体口径**（累计降幅 vs 差分、阈值取轨迹层同源值、向上段返回 None、
   无 tcp_targets 才按关节角兜底）规格只给了"首个非零下降节点"六个字，实现口径与理由写在
   `first_descent_node_index` 的 docstring，并在 9 组合成段参数化用例 + 1 组真实规划输出对照
   用例里钉住（含"前导零位移节点被跳过""向上段不产事件""1e-10 m 不算"）。
4. **stage_enter 也记 FAULT_HOLD/FAULT_UNCONTROLLED**：规格要求"每次阶段变更时记录"，
   而故障保持本身就是一次改写；顺序上 failure 在前、FAULT_* 的 stage_enter 在后，因此
   §2.8.2 末段"原始阶段、最终 FAULT_HOLD 阶段、实际成功三者分别存储"在同一份快照里齐备。
   代价是每次调用多一条事件，仍在上限内。
5. **failure 记一次、result 记一次、descent 记一次**（`_failure_done` 等标志）。规格写的是
   "事件仅内存追加且有界（每阶段首次进入/**首次**下降发送/结果）"，"首次"读作"每次调用至多
   一条"。因此 `_early_fail` 已记 failure 后进入 `_fault_result` 也不会重复。
6. **`_refuse` 不记 failure**（见 §5）。
7. **不确定事项的处置原则**：三态里凡"不能证明"一律 unknown、绝不折算成 False/rejected；
   trace 任何路径都不写盘、不起线程、不重试、不改写异常；不修改任何运动判据、阈值、
   GraspResult/VisionInterface 字段与 common_interface；不改 `plans/main`；不 pip install、
   不 git commit。
