## 2. 实现说明（文件 + 关键符号）

### 2.1 `configs/motion_params.py`

**抽取共用内部函数（避免复制整套校验造成双份维护）**：

- `_read_profile_json(profile_path) -> (raw, d)`：读盘（`_reject_constant` 拒 NaN/Infinity）、
  顶层键 `_require_keys`，返回原始 `raw`（real 报告绑定要对它求 `parameter_sha256`）与校验后
  的 `d`。不判断 status——状态门槛留在各入口，保持对外行为逐字不变。
- `_parse_and_validate(profile_path, d, status, *, check_hashes) -> MotionParams`：加载主体。
  顺序与原 `load_motion_params` 一致：`_parse_model`→`_parse_collision`→URDF 存在性+限位读取
  →（`check_hashes=True` 时）URDF 哈希、电机校准文件存在性+哈希→`_parse_joints`→
  `_check_limit_intersection`→`_parse_workspace`→构造 `MotionParams`（`_parse_*` 逐组，内含
  `_null_check`）→`_check_gripper_table_coverage`。**不**判 status 模式、**不**做报告绑定。
  `status` 原样写入返回对象，不改写、不落盘。

**三个公开入口各自决定门槛**：

- `load_motion_params(profile_path, *, mode)`：签名、docstring、状态/报告门槛、调用顺序全部
  保持原样——real→`check_hashes=(mode=="real")`、仅 real 调 `_check_report_binding`；
  mock→仅要求 URDF 存在（不核哈希），与抽取前完全一致。行为逐字不变由 56 个既有用例零修改
  通过证明。
- `load_calibration_motion_params(profile_path)`（**新增**）：接受 status∈{draft,verified}，
  其他（含 simulation）以自措辞拒绝并点明"仿真配置不属于标定链、生产运行请用
  `load_motion_params` 的 real/mock 模式"；随后 `_parse_and_validate(..., check_hashes=True)`
  ——校验强度与 real 同款（含资源哈希），**唯一差别**是不强制 verified、不调 `_check_report_binding`。
  不新增 `mode="calibration"`，生产入口不可达此豁免。

**文档面**：模块 docstring 增补标定入口用途与"三个加载入口不可混用"说明；新增 `__all__`
（含 `load_calibration_motion_params`，同时登记 `load_motion_params`/`load_calibration_profile`
的分工）——仓库无 `import *` 依赖，加入 `__all__` 不改变任何现有导入语义。

### 2.2 `tests/test_calibration_loader.py`（23 用例）

draft 样例构造：`_draft_profile_path()` 以仿真 profile（全字段非 null）的**副本**为底，改
`status="draft"`、`verification=None`，回填两份真实资源哈希（`_actual_urdf_sha256`/
`motor_calibration_sha256`），经 `write_profile` 落临时目录；负向用例在回填之后用 `mutate`
覆盖单字段。真机 `calibration/REAL_ARM/PC/profile.json` 仅**只读**加载做集成用例（前后 SHA256 相等，不修改）。

## 5. 问题与限制

- 任务书提示"真机 profile 当前 draft 且**含 null**，正好做拒绝用例"。实测仓库
  `calibration/REAL_ARM/PC/profile.json` 当前 draft，但除 `verification`（draft 常态 null，
  且属被豁免的报告绑定项，加载器不应因它拒绝）外**全部运行期字段已非 null**、两项资源哈希
  与真实文件匹配——即它能被标定加载器**成功读取**，而非拒绝。据此把真机 profile 用作
  **只读集成接受用例**，把"拒绝 null/未测"改用**注入 null 的仿真副本**覆盖（parametrize + 数组元素
  null）。不修改真机 profile。此为对任务假设的自主校正，记入 §7。
- 未新增 `mode="calibration"`，也未给 `load_motion_params` 加运行时未知 mode 守卫——那会改变
  既有对外行为（当前未知 mode 落到"仅 URDF 存在、无报告绑定"的宽松分支，属既有语义）。规格只要求
  "不新增该 mode 暴露给生产"，未要求主动拒绝任意字符串，故保持原样。T09 里以"mock/real 均拒 draft、
  draft 无法经任何 mode 得到标定豁免"证明隔离，不测未定义分支。

## 7. 自主决策

1. **共用函数抽取边界**：把"读盘+顶层键校验"抽为 `_read_profile_json`，把"分组解析+资源
   存在性/（可选）哈希+限位交集+表覆盖"抽为 `_parse_and_validate`；**状态门槛与报告绑定留给
   各公开入口**。理由：两门槛是三个入口唯一真正的差异点，抽进共用函数就会逼出 flag 或 mode，
   违背"逐字不变"；留在入口侧既零复制校验逻辑，又让 real/mock/标定各自演化。校验主体（含全部
   `_null_check`）单点维护，无第二份。
2. **draft 样例构造方式**：以仿真 profile 副本改 status+回填真实资源哈希，而非手抄一份大 JSON。
   理由：仿真 profile 已是"全字段非 null 且结构合法"的单一真值源，副本天然满足"完整 draft"，
   负向用例只需在其上 mutate 单字段，测试意图最小化、可读性最高。真机 profile 只做只读集成校验。
3. **真机 profile 假设校正**：见 §5，改为只读接受用例，拒绝 null 用注入副本承担。
4. **`__all__`**：新增以登记 P4-03 衔接的公开入口；确认仓库无 `from configs.motion_params import *`，
   故不改变任何现有导入。
5. 不确定事项均按"不削弱断言、不放行 null、不改生产 loader 行为、不触碰范围外文件/真机 profile"
   的原则就地自主处理并记录于此。
