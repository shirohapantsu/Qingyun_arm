  属调用方程序错误抛 VisionHardError 不静默取 0"、单候选缺深度属过滤而整帧故障属硬错误、

  TYPE_CHECKING 块内）。

## 5. 问题与限制

- **耗时**：新增 48 例合计 0.13s（5 条子进程用例各 ~0.02–0.08s，其余为纯内存断言）；
  全量 577.10s 与 P1-02 的 576.71s / DEC-001 登记的 ~570s 基线一致，本任务不新增慢用例。
  Mock 组 6 例复用 session 级 `params` fixture（既有），不重复加载仿真 profile。
- **变异自查工具是 /tmp 下的一次性脚本**（`p103_mutation_check.py`），未进仓库：它只
  做"备份→改→跑→还原→SHA 核验"，结果已逐条登记在 §3，脚本本身不属交付物。
- **桩不实现任何功能，因此"能跑通"不等于"能用"**：三个模块在 P2/P3/队友替换桩体前，
  任何真实业务流程都会得到硬错误。P1-04/P1-05 的 plan/main 用例必须经
  `tests/support_upper.py` 的替身 monkeypatch 掉 `qingyun.plans.base` 里的模块引用
  （P1 §3.6 末段），不能指望桩返回可用数据。
- **`get_target` 桩不校验 `ignore`**：真实实现里"负值/非整数 → VisionHardError"是
  P3 的输入校验（P3 §3 末段），桩只是无条件抛同一异常，因此本任务不能据此宣称
  P3 的校验已被验证。测试里"任何参数都抛"这一形态在替换后仍需保留，但"消息含未实现"
  那半截必须删除（B 组已按此分组）。
- **签名用例按"注解名字字符串"比对**：桩用 `from __future__ import annotations`，
  注解是字符串；真实现若不加该 future import，注解会是类对象。`_annotation_text`
  把两种形态归一到名字，所以本组用例不强迫队友保留 future import。
- **重依赖黑名单依赖目标机装了哪些包**：本 env 未装 sounddevice/httpx/cv2/ultralytics
  等，纯 `sys.modules` 检查在这些项上会空转。已用 AST import 白名单/黑名单补上环境
  无关的一重（M4 变异在装了 numpy 的机器上同时打掉两重，证明两重各自有效）。
- **`qingyun`/`qingyun.grabbing` 仍是命名空间包**（无 `__init__.py`）：桩与既有模块的
  导入风格一致；若队友实现 P3 时新增 `__init__.py` 会改变包语义，`test_干净进程import
  成功且无输出无重依赖` 的 `qingyun_loaded` 精确集合断言会立刻报错，属预期的守门。
- **mock 的 `timeout_s` 默认值是真机无关的名义值 5.0**：真机用驱动私有常量 2.0（待实测，
  P1 §4.1 末段）。测试只断言"形状对等 + 参数被原样记录"，不断言两边默认值相同
  （见 DEC-P1-03-B）。
- **桩阶段的 `__all__` 封闭集断言偏严**：若 P2/P3 想在同名文件里增加公开工具函数，
  需要同步改 `tests/test_module_stubs.py`。这是有意的（契约面显式化），但会在替换时
  产生一次"测试要跟着改"的工作量，已在 B 组分组与 §6 交接里写明。
- **P1-04 跨界需求**：无。FakeVision（`tests/support_upper.py`）明确不属本任务，未创建；
  `qingyun/plans/` 未创建。

## 7. 自主决策

- **DEC-P1-03-A（注解依赖全部走 `from __future__ import annotations` + TYPE_CHECKING）**：
  候选①运行时真 import `configs.app_config.AppConfig` / `configs.common_interface.*`
  ——会把 `motion_params`（app_config 依赖它）与 numpy 拉进桩的 import 链，与
  "P1-03 只交付契约面、P3 §2 明确限制 vision 的依赖方向"相冲突；候选②裸字符串注解
  （`def init(cfg: "AppConfig")`）——可读性差且失去 IDE/类型检查收益。取③：
  future annotations + TYPE_CHECKING 块，运行时零依赖、静态面完整。代价：
  `inspect.signature` 看到的是字符串注解，故签名用例按**注解名字**比对，并用
  `_annotation_text` 归一（兼容队友不加 future import 的写法）。
- **DEC-P1-03-B（mock `timeout_s` 取名义值 5.0，不 import 真机私有常量）**：真机默认是
  `motor_control._INIT_TIMEOUT_S = 2.0`，且 §4.1 明确"deadline 默认值沿用驱动常量作为
  待实测值"。若 mock 直接 import 这个私有名：①把下划线私有常量升格成跨模块契约；
  ②P1-06 真机实测改数值时会静默改变 mock 语义；③让 tests/mock_motor 依赖驱动实现细节。
  故 mock 侧在 `MOCK_INITIALIZE_TIMEOUT_S` 上取任务建议的名义值 5.0，并把"数值不比对、
  形状逐位比对"写进用例与注释。生产调用形态（三个 keyword-only 参数、全带默认值）
  由对等用例保证兼容。
- **DEC-P1-03-C（构造仍不自动调用 initialize）**：真机 §4.1 是"默认构造调用它一次"，
  理论上 mock 跟随更"真机对等"。但 mock 的现状是构造即得可用仿真体，既有运动回归
  （test_grasp_flow 全 46 例经同一构造）依赖该现状；自动调用会给每个实例凭空加一条
  台账记录，把 P1-05 要测的"initialize 恰好一次"断言变成噪声。任务明确"保持不变"，
  故只补方法、不改构造，并在 docstring 与用例里写清理由。
- **DEC-P1-03-D（`initialize_calls: list[dict]` 单一状态字段，不加 `initialized` 布尔/计数副本）**：
  "调用次数 = len(台账)"避免两个字段可能互相矛盾；dict 快照保留三个参数的实际取值
  （标定脚本的 `enable_torque=False` 只读路径与 P1-06 的握手用例都要按值断言）。
  未同步改 `all_faults_off()`——它只负责故障注入开关，清生命周期台账会让
  "reset 后仍能看到 initialize 发生过"这一审计信息丢失（有用例钉死）。
- **DEC-P1-03-E（桩消息用"统一前缀 + 该函数契约要点"两段式）**：候选①只写
  "ASR 未实现（P2 替换本桩）"（P1 §3.6 字面）——操作者看不出这次调用本应发生什么；
  候选②带完整契约长文——异常消息不该当文档读。取③：前缀严格统一（便于 grep 与
  测试按 `startswith` 钉死），后接一句该函数最容易被误用的契约点（含"桩不返回
  空串/invalid/目标、init 故障不伪装 NoTarget"）。任务给的字面文案作为前缀保留。
- **DEC-P1-03-F（NoTarget 与"合法空串/invalid"一样被列为禁返回值，并各写一条反向断言）**：
  P1 §5 里空串、invalid、NoTarget×3 都是**正常业务分支**；桩若给出任何一个都会让
  上层"看似跑通"。因此三个桩的消息与测试都显式否定这三条路径（B 组三条用例 +
  `test_桩公开调用一次都不正常返回`），并以 M1/M6 变异证明这些否定有牙。
- **DEC-P1-03-G（import 零副作用做两重：干净子进程 sys.modules + AST import 白名单）**：
  单靠子进程会在"目标机没装该包"时空转（本 env 正如此）；单靠 AST 无法排除
  `importlib.import_module("cv2")` 之类的动态路径。两重并列，且用 M4 变异同时打掉
  两重以证明二者都非摆设。`HEAVY_IMPORTS` 与 `STUB_ONLY_ABSENT_IMPORTS` 分列，
  是因为真实现会合法导入 configs/numpy，但**永远不该**导入设备/云运行时——
  前者随替换失效、后者是 P2-T11/P3-T17 的常驻要求。
- **DEC-P1-03-H（测试分 A 常驻/B 桩阶段两组，并在文件 docstring 与 §6 交接里点名）**：
  P1 §1 说"P2/P3 在原文件上替换实现"，若把"调用即抛"写成不可分层的断言，队友换实现时
  只能整文件删测试。分组后：签名/异常分层/路径稳定/import 零副作用留得下来，
  桩专属断言有明确的删除清单（含"负值 ignore → VisionHardError 半截建议保留"）。
- **DEC-P1-03-I（不新建 `qingyun/grabbing/__init__.py`，不创建 `qingyun/plans/`）**：
  包内既有模块都靠隐式命名空间包 + 根 conftest 的 sys.path 注入工作，补 `__init__.py`
  属改变包语义的越界动作；`qingyun/plans` 归 P1-04。测试里额外用 `qingyun_loaded`
  精确集合断言把"当前包链只到本桩"钉住，将来任何一方改包结构都会显式暴露。
- **DEC-P1-03-J（vision 桩只重述契约，不写任何"预防性"接口便利面）**：不加
  `reset()`、`shutdown()`、`is_configured()` 之类"队友大概会需要"的公开名（M5 变异
  正是针对这一约束）。P3 §2 的依赖方向与 P1 §3.6 的封闭契约面优先于个人偏好；
  确实需要的接口由 P3 实现时随真实用例一起提出。
