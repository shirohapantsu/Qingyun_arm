## 2. 实现说明

### 2.1 `scripts/check_deployment.py`（工具）

关键符号：`load_manifest`（严格 schema+路径安全+密钥拒绝，违例抛 `ManifestRejected`→退出 2）、
`run_deployment_check`（返回 `(退出码, verdict dict)`）、`main`（CLI）。

- manifest schema v1 在工具 docstring 与文档 §2.3 同一份逐字钉死：顶层必填
  `schema_version`(整数1)/`git_commit`(40位小写hex，形态校验)/`motion_profile`
  `{relative_path,sha256,verification_report}`/`resources`[{`relative_path,sha256,role,reports`}]
  /`reports`[{`relative_path,sha256,kind`}]，可选 `provenance∈{measured,simulated}`；
  未知键/缺键/坏值一律拒绝（沿用 configs 两加载器的 `_require_keys` 严格风格）。
  相对路径相对 manifest 所在目录解析（P1 §3.1/D16 惯例）；拒绝绝对路径、反斜杠、
  空段/`.`/`..`、全清单路径重复声明。
- 判据 a `resource.exists`/`resource.sha256`：motion profile、每个报告、每个资源逐项
  存在+实算 SHA256 比对（`sha256_file` 流式，与标定链同口径；schema 层已拒绝非
  64 位小写 hex，堵占位值）。
- 判据 b `report.pass`（kind=profile_validation）：可解析为 JSON 且 `overall_pass`、
  `operator_reviewed` **存在且为真**——字段与 truthiness 口径逐字对齐生产
  `_check_report_binding`（`not report.get(k)` 即失败），缺字段不允许缺省通过；不发明
  字段。
- 判据 c `report.demo_acceptance`（kind=demo_acceptance）：**复用**
  `scripts/fit_grade_threshold.validate_demo_acceptance`（P4 §3.1 严格 schema + 四键），
  含 null → "不完整、不可验收"判 FAIL 并列出 `missing_fields`；schema 违例同样拒绝。
  不复制其逻辑、不放宽。
- 判据 d `motion_profile.real_reload`：直接调用 `load_motion_params(path, mode="real")`，
  捕获任何异常即失败（生产判据原样生效，工具不复制不放宽一条）；失败 detail 逐字带
  P5 §6/落地方案 §9.2 不豁免条款。工具**无**任何豁免开关；`provenance` 只回显进
  verdict、绝不参与判定。
- 判据 e 密钥拒绝：路径基名 `secrets.json`、前缀 `secrets.`、路径段 `secrets`、或
  manifest **任意字符串值**（含键名）递归出现 `SECRET_KEYS`（`dashscope_api_key`/
  `deepseek_api_key`，import 自 `configs.app_config` 单一来源）→ 整体拒绝（退出 2，
  先于任何存在性检查）；工具从不读取/哈希/校验 secrets 文件内容。
- 两项补充强制项（只收紧、不放宽）：`report.reference`（资源关联报告与
  `verification_report` 不得悬空，绑定报告 kind 必须 profile_validation）；
  `report.binding_consistency`（manifest 声明的绑定报告与 profile 内部
  `verification.report_path` 归一后必须同一文件——"对应报告"只允许一套真相；profile
  不可解析/无 verification 时记"不适用"通过，那些缺陷由 a/d 独立把闸，见 §7-C）。
- 机器可读结论：stdout 逐项 `[ok ]/[FAIL]` + `VERDICT=…` 行 + 完整 JSON verdict
  （verdict/checks[check_id,target,ok,detail]/counts/failed/notice/git_commit/
  provenance）；`--report PATH` 另存同一 JSON。对部署树全程只读（测试有哈希快照断言）。
- 退出码：0 全过；2 manifest 不可信/不可用（含密钥拒绝）；3 强制项未满足。argparse
  缺参非零（--manifest required）。
- import 机制：与 `scripts/calibrate.py` 同款 ROOT→sys.path bootstrap；
  `from scripts.fit_grade_threshold import ...` 在 `python scripts/check_deployment.py`
  与 `import scripts.check_deployment`（PEP 420 命名空间包，项目根在 sys.path 时）
  两种形态下都实测可用（§3 #4/#5）。

## 5. 问题与限制

- 工具校验的是"清单声明与树内容一致 + 报告字段 + 生产 loader 可加载"；**不**判定
  `provenance`/`git_commit`/报告内容的**真实性**（目标机 commit 一致性、样本真伪属
  B 类步骤 1 与人工复核），也不校验部署树外的任何东西（依赖安装、设备等）。
- `report.binding_consistency`/`report.reference` 是超出任务书 a–e 列举面的补充强制项
  （只收紧）；profile 缺 verification 时该项记"不适用"通过而 d 独立判 FAIL——不影响
  非零退出总语义。
- 报告 kind 为闭集两类（工具知道其真实 schema 的）；CAL-040/041、足迹、混淆矩阵等
  报告 schema 属 P4 §2.3/队友侧未冻结，暂不能纳入离线判定面（纳入即"发明字段"），
  已在文档 §2.3 写明"新增类别须先修订清单与工具"。
- `git_commit` 仅形态校验；secrets 拒绝判据为文档 §2.2/§2.4 明写的三条（见 §7-E）。
- 首轮 1 失败为测试自身断言定位错（needle 查错字段），修测试后全绿；未削弱任何断言、

## 7. 自主决策（DEC 候选，交主 agent 归档）

- **AD-P5-02-A（正向分支可达，未降级）**：任务书预许可"若 verified+报告绑定使纯合成
  fixture 无法通过 d 的正向分支，用 simulated 树证明机制被真实调用"。读
  `configs/motion_params.py` 实况后确认：`_check_report_binding` 的 stages 证据循环对
  `stages={}` 报告自然放行（`report.get("stages") or {}` 空迭代），配合
  `test_real模式能加载一份完整验收过的配置` 的既有配方即可在 tmp_path 合成一棵
  **真实通过生产 real loader** 的树。选择：实现正向用例（强于"仅负向证明"），树以
  `provenance="simulated"` 如实标注、只在 tmp_path、不进 tests/fixtures、不放宽生产。
  验证：§3 #2/#7。风险登记：若 P4/后续收紧 promote 报告形态（如强制八阶段+physical），
  该合成报告需再生成，工具无需改。
- **AD-P5-02-B（不实现 manifest 生成子命令）**：任务书默认倾向"验证面强制、生成面手写
  由文档给模板"。理由：资源的 role/关联报告/kind 是打包人的语义声明，目录遍历只能
  生成 relative_path+sha256 骨架，生成器无法产出合法清单，反而制造"跑过生成器=合规"
  错觉；故仅提供 `check` 面，模板钉在文档 §2.3。验证：不适用（未实现即无测试面）。
- **AD-P5-02-C（两项补充强制项）**：`report.reference` + `report.binding_consistency`
  超出任务书 a–e 字面列举，为兑现 P5 §5"逐项记录…对应报告"的**单一真相**含义（manifest
  指 A、profile 内绑 B 时发布验收面出现两套绑定）。binding_consistency 在 profile 不可
  解析/无 verification 时记"不适用通过"——避免与 a/d 重复报因、把归因留给真正有牙的
  判据。均为只收紧的附加项，不影响任何原判据。验证：`test_verification_report未声明或
  kind错配失败` 两用例、正向树全绿。
- **AD-P5-02-D（报告 kind 闭集两类）**：b/c 判据不发明字段——profile_validation 用
  生产 loader 实际消费的 `overall_pass`/`operator_reviewed` 对；demo_acceptance 复用
  `fit_grade_threshold.validate_demo_acceptance`（四键判据即 configs/demo_acceptance.json
