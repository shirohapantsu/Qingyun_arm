## 2. P1 Fix

### Issue ID

FINAL-P1-001

### 原问题

CHECK（及闭爪后 `_replan_after_close`）对 lift/transfer/lower/retreat/return 的预规划校验全部以 `q_ref`（接触位形，抓取区）为每段起点构建；实际执行时 `_execute_step` 每段从上一段终点的实测位形构建。两者是不同路线：名义 lower 退化为抓取 XY 上约 2mm 的伪段、名义 retreat 在抓取 XY 上升——放置区的竖直下降与撤离路径在动作前校验中完全缺失。技术文档 §5.3/§6.3 要求 CHECK"预规划、校验整条名义路线"未被真正满足。审阅报告的动态复现：放置区 z∈[0.030,0.046] 障碍下 CHECK 放行，455 条指令提交后才在 LOWER 报 COLLISION。

### 根因

`arm_control.py` 的校验循环（`_build_post_grasp_steps` 原 :609-612）对每个 step 都传同一个 `q_ref`，各段校验起点未按真实执行顺序（lift 终点 → transfer 起点，依次类推）链式传播。`_preplan` 的 approach/descend 循环（原 :503-506）存在同一根因：descend 以 `q_now`（home 位形）构建，校验的是 home XY 上另一条竖直线，而非实际执行于抓取 XY 的下降段（审阅历史中未点名，本轮修复时按同一缺陷模式识别并经代码走查证实）。

### 修改方案

最小可靠修复：校验循环改为链式构建——每段以"上一段的规划终点 `seg.end_joints`"为起点构建并校验，链起点为 `q_ref`/`q_now`。这与运行期 `_execute_step` 逐段从实测起点重建接力的路线一致（理想跟踪下实测终点=规划终点；偏差场景仍由既有 `_play_with_offset_guard` 兜底重校验）。接触开度区间两端点各走一遍整条链的既有策略保持不变（`_preplan` 循环两次调用同一构造函数）；闭爪后 `_replan_after_close` 复用同一构造函数自动获得链式行为。不改公共接口、不改协议语义、不改 PlanStep 构建闭包、不降低任何校验标准。

### 修改文件

- `qingyun/grabbing/arm_control.py`（生产代码，两处循环）
- `tests/test_grasp_flow.py`（新增 1 个回归测试）

### 修改内容

- `_build_post_grasp_steps` 校验循环：`step.build(q_ref)` → `step.build(q_chain)`，每段校验后 `q_chain = seg.end_joints`（lift → transfer → lower → retreat → return 依次接力；retreat/return 使用释放开度、起点为 lower 规划终点，与 RELEASE 只动夹爪的实际执行一致）。
- `_preplan` 校验循环：同样链式传播，`descend` 从 approach 规划终点（`q_above`）构建，校验的竖直线与实际执行一致。
- 两处均附根因注释。

### Regression Test

新增 `tests/test_grasp_flow.py::test_仅真实链式放置路径被阻挡时在CHECK就被拒绝`：在放置点 (0.32, 0.055) 正上方注入仅阻挡"真实链式 lower 竖直段"的障碍柱 `x∈[0.308,0.332], y∈[0.043,0.064], z∈[0.030,0.046]`（低于 transfer 终点持物盒下沿 ≈0.069——旧端点检查放行；远离抓取区——链前段放行），抓取点 (0.38, −0.05)。断言实际业务行为而非"不崩溃"：`status is COLLISION`、`stage == CHECK`、`recovery_required is False`、`command_count == 0`、实例不锁存。相邻边界核对：既有 `test_放置位姿不可达时在CHECK就被拒绝`（端点不可达路径）保持通过；正常全流程 `test_一次下发对应一次完整同步调用`、`test_同一控制器连续两次调用都成功`（重复调用）通过，确认链式校验未引入误报拒绝。

### 验证结果

- 修复前运行新测试：**FAIL**——`stage=FAULT_HOLD`（碰撞在 LOWER 执行期才暴露、指令已提交），精确复现原问题。
- 修复后运行新测试：**PASS**——CHECK 拒绝、零指令、不锁存。
- 受影响模块及全量回归通过（见 §4/§6）。

### 当前状态

**FIXED**

## 3. P3 Fix

### Issue ID

FINAL-P3-005

### 原问题

`ByteTransport.write/read` 增加 `timeout_s` 后，协议层以关键字传参；只实现旧签名 `write(data)`/`read(n)` 的注入对象在第一条命令即抛 `TypeError`（被包装为 `MotorCommunicationError`，`__cause__` 保留）。《电机修改.md》§3"向后兼容，不影响任何调用方代码"的声明对调用方成立、对实现方不成立，表述过强。

### 根因

"可选参数向后兼容"只覆盖调用侧；Protocol 契约变更（要求实现方接受 `timeout_s` 并落实时限）未在修改报告中如实表述为实现方破坏性变更。

### 修改方案

三选一（报告建议：勘误成文 / 能力检测回退 / 维持现状）中选择**风险最低、改动最小、易验证**的文档勘误。不做能力检测回退：`ByteTransport` 是驱动内部测试缝而非冻结公共接口，仓内全部实现均已更新，回退分支会引入一条无法被真机验证、且可能静默削弱时限语义的新代码路径，与"不通过默认成功隐藏失败"的原则相悖。

### 修改文件

- `电机修改.md`（§3 接口兼容性对应条目）

### 修改内容

将该条目改写为如实成文：声明原表述只对调用方成立；对实现方是破坏性契约变更；说明失败模式（TypeError → MotorCommunicationError，可诊断）；明确新契约要求实现方接受 `timeout_s` 并落实有限阻塞；说明仓内无旧签名实现残留及外部旧签名 transport 的兼容路径未实现的原因。无代码改动。

### Regression Test
