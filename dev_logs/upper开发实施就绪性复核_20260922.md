## 1. 裁定

**当前方案仍有问题，整套实施文档尚不能作为无需补充解释、可直接照做并据以验收的 upper 开发规格。可以立即开展 P0；其余阶段可开展无争议的局部实现，但不宜以“全部冻结”状态整体派发。**

这不是因为 upper 尚未实现就否定方案。`grade` 迁移、空模块、draft profile、待测 K/places 都是已登记的工作。真正影响就绪性的，是修订记录与正文不一致，以及 mock 注册表、驱动生命周期、标定证据来源等接口没有闭合。

## 2. 主要发现

### F01｜阻断 P3 几何实现：R02 修正没有进入实际正文

证据：

- `dev_logs/upper开发前复审后修正.md:41` 声称已重写几何管线，并新增 P3-T19/T20。
- `docs/实施文档/P3_视觉检测与目标选择技术文档.md:93` 仍定义 `z_top` 为 base 系高度，下一行却要求以它作为深度 deproject。
- 同文件第 97–98 行仍使用“像素长短边 × Z / f”和图像长轴角转换。
- 测试表实际止于 T18；全文没有 P3-T19/T20，交付物却要求 T01–T20。

影响：基座系高度与相机光轴深度混用会直接给出错误 XY；相机倾斜、畸变和透视情况下，当前尺寸/yaw 计算也不能作为普适公式。

独立针孔反例（本次用 Python 标准库实算）：相机位于桌面上方 0.5m、垂直向下；顶面点 base 坐标 x=0.1m、z=0.04m；fx=600px。真实相机深度为 0.46m。用 0.04m 反投影得到 x≈0.00870m，仅 X 就偏差约 91.3mm，远超 4mm。

修订要求：冻结 RGB/深度各自坐标系、D2C 输出的深度语义、去畸变与像素坐标配套规则；中心用相机系深度反投影再变换，或明确高度平面上的射线求交；尺寸/yaw 使用经过验证的 base 系几何估计。补齐倾斜、平移、fx≠fy、边缘及畸变测试。

**不能直接把修正记录中的“四角射线与桌面求交”当作完整修复。** 高于桌面的物体，其图像外接矩形反投影到桌面，并不自动等于实际水平长宽。例如上述相机高度下，位于 z=40mm 的 50mm 水平线段投影到桌面会变成约 54.35mm。图像 OBB 也不是物体真实三维四角。须明确这只是保守占用近似，还是实际尺寸估计，并分别验证过滤、分级和 yaw 的适用条件。

几何依据：[OpenCV 相机模型与坐标变换官方说明](https://docs.opencv.org/4.13.0/d9/d0c/group__calib3d.html)。

### F02｜高：mock 的预检注册表与运行注册表没有接通

证据：

- P5 第 21、44 行：用 `MOCK_REGISTRY` 预检，并由其提供注入名义 K 的 Plan 变体。
- P5 第 40 行：进入 `run_session(cfg, arm)`，没有传入注册表。
- P1 第 215、227 行：会话签名没有 registry，主循环直接 `PLAN_REGISTRY[task](arm)`。
- P1 第 146 行：生产 StrawberryPlan 的 K 在 P4 前为 None。

影响：按示例照做，可以出现“mock 预检通过，实际运行却创建生产 Plan”的情况，名义 K 没有进入运行路径。编码者必须自行增加参数或修改全局注册表才能补齐。

修订要求：明确采用显式注册表注入，或明确入口对会话所用注册表的替换机制；预检与实际构造必须使用同一注册表。增加“生产 K=None、mock K 有效且两个任务都实际抓取”的验证。

同时明确 `run_session` 与入口各自负责哪些初始化：目前文字只说“含冷启动复位与顶层循环”，P5 代码块又没有显式调用 vision.configure/init。统一 SimTime 已写对，但不足以证明完整装配已闭合。

### F03｜高，真机启动前：驱动握手仍是要求摘要，尚未冻结生命周期

证据：

- P1 第 185–193 行仍以默认 `Sts3215MotorController(params)` 为入口，并附“整理公开接口”的要求。
- 现有 `motor_control.py:1488` 构造时调用 initialize；第 1533–1534 行直接进入 configure_torque(True)，没有目标预置握手。
- `scripts/validate_home_waypoint_motion.py:452` 使用 initialize=False，再以 enable_torque=False 初始化；第 463 行起明确目标预置本身可能隐式上力，之后核对 Goal_Position、六轴力矩与位置变化。

不能把“现有驱动未实现”本身当作方案缺陷，P1 已登记改造任务。剩余缺口在于：没有明确新接口签名、默认构造是否改走新握手、初始已上力如何处理、各失败阶段的清理边界，以及读回失败后能否宣称已失能。

特别是 P1 同时规定“部分使能失败逐轴失能清理”与 terminate 不追加命令，须明确前者属于驱动初始化失败处置，后者从哪一边界开始约束运行期。不能笼统复制校准脚本的退出卸力逻辑到生产退出路径。

修订要求：补一个明确的启动状态/调用顺序表和公开签名，落实旧目标不一致、部分上力、读回中断、位移超限的结果与清理责任。假总线验证后才能进入真机启动验证。该项不阻止先写 Plan 的离线单测。

### F04｜高，P4 抓放验收工具：有入口名称，但证据产生链仍缺关键来源

证据：

- P4 第 76–79 行要求在 draft 上运行 ArmController，输出既有 validate 接受的 JSONL，包含 `began_descend`。
- `configs/motion_params.py:1191` 的生产/仿真加载器均拒绝 draft；第 1308 行的 CalibrationProfile 只是总线采集最小参数，不能直接替代 ArmController 所需的完整 MotionParams。
- 现有 `validate_home_waypoint_motion.py:64` 有临时副本改为 simulation 后加载的专用做法；P4 尚未明确复用这一做法还是新增校准加载入口。
- `arm_control.py:997` 将故障返回阶段覆盖为 FAULT_HOLD/FAULT_UNCONTROLLED；公开 GraspResult 没有“曾开始 DESCEND”字段，也没有公开阶段事件接口。
- `scripts/calibrate.py:2768` 恰好按 began_descend 筛选试验分母。

影响：仅凭最终 GraspResult，不能可靠区分 APPROACH 失败与 DESCEND/后续失败，因而不能可靠自动生成统计分母。把所有 recovery_required=True 当作 began_descend=True 会记错试验。

修订要求：明确完整 draft 参数的校准加载方式，保留真实 profile 身份及哈希；明确 began_descend 来自运动阶段事件、可靠的专用记录钩子，或受控人工观察字段，不能从最终故障码反推。若允许内部临时 simulation 副本，须明确其只是加载适配，不改变原始证据的 hardware 来源。

补齐兼容现有 Record 包装的样例及导入测试；`trial_summary` 不能代替 pick_place 分母实际读取的 sample 记录。修正记录声称新增的 P4-T08 当前也不在测试表中。

### F06｜中高，真机样本准入前：长宽低估误差仍未形成约束

## 3. 较小但应顺手收敛的接口问题

- P1:180 在读取 cfg 前按默认 logs 初始化日志，cfg.log_dir 的最终应用没有定义；同一行又说配置加载失败时尚无 JSONL，与顺序矛盾。确定最终日志目录及配置失败的日志行为即可，不需要新审批流程。

- P4:37 使用 get_target(0) 做逐样本验证，宜明确每次场景只放一个待测样本，或另设关联/全候选采集机制，以落实“一一对应”和未检出计分母要求。
