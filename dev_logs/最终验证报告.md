## 3. P1 Verification

### 原问题与根因

最终审阅指出，CHECK 对 lift、transfer、lower、retreat、return 分别用同一抓取接触位形 `q_ref` 建段，而运行时则从上一段的实测终点接力建段。因此放置区真实的竖直 lower 路径可能根本没有被动作前校验，违反技术文档 §5.3 和 §6.3 对“预规划、校验整条名义路线”的要求。

### Fix 修改与当前行为

当前代码在 `_preplan()` 中将 approach/descend 的规划起点经 `q_plan = seg.end_joints` 链式传递（`qingyun/grabbing/arm_control.py:502`）。在 `_build_post_grasp_steps()` 中，对 lift → transfer → lower → retreat → return 使用同样的 `q_chain` 传播（`qingyun/grabbing/arm_control.py:613`）。

这不是只在调用方绕过症状：`_execute_step()` 仍按段读取实际起点、构建、校验和回放（`qingyun/grabbing/arm_control.py:630`）。理想跟踪时，CHECK 的规划终点链与运行期建段链一致；发生实际起点偏差时，既有 `_play_with_offset_guard()` 继续负责重新校验或拒绝不可重建的竖直段。没有发现硬编码障碍坐标、吞异常、默认成功、降低校验阈值或针对测试输入的特殊分支。

### Regression Test 与实际验证

新增测试 `test_仅真实链式放置路径被阻挡时在CHECK就被拒绝` 在放置点上方加入只会阻挡真实 lower 段的柱状障碍（`tests/test_grasp_flow.py:221`）。它验证业务结果而非仅验证“不崩溃”：

- `status is COLLISION`；
- `stage == CHECK`；
- `recovery_required is False`；
- `command_count == 0`；
- 控制器未锁存故障。

独立执行该回归测试、一次完整同步调用和连续两次调用：**3 passed**（80.39s）。随后全量测试再次通过。该测试确实覆盖修复前会漏掉、而修复后须在 CHECK 拒绝的真实链式路径。

### 最终状态

**VERIFIED_FIXED**。

## 4. P3 Verification

### 原问题与根因

FINAL-P3-005 的问题不在核心运动语义，而在《电机修改.md》的兼容性表述。`ByteTransport.write/read` 新增 `timeout_s` 后，协议层使用关键字调用；因此旧实现 `write(data)` / `read(n)` 的 transport 对象对实现方并不兼容。此前“向后兼容，不影响任何调用方代码”的表述覆盖了调用方，却错误外推到实现方。

### Fix 修改与当前行为

`电机修改.md` §3 已明确勘误：调用方已同步更新；实现方契约是破坏性变更；外部旧签名 transport 会因 `TypeError` 收到可诊断的 `MotorCommunicationError`；本轮没有实现可能削弱时限语义的能力探测回退。该表述与当前 `ByteTransport` Protocol（`qingyun/grabbing/motor_control.py:772`）和协议层关键字传参（`qingyun/grabbing/motor_control.py:993`、`:1048`）一致。

### Regression Test 与实际验证

该项是文档正确性修复，不应为维持错误兼容性添加回退逻辑。除全量驱动测试外，本轮以独立旧签名 transport 调用 `StsProtocol.read_registers()`：实际得到 `MotorCommunicationError`，且 `__cause__` 为 `TypeError`，与勘误文本一致。又以 `SerialTransport.wrap()` 包装独立 serial-like 对象，确认写预算 `0.015s` 落到 `write_timeout`，读预算 `0.020s` 受 `0.001s` 分片限制。

因此，修复没有改变正确的公共 `MotorController` 接口，也没有将错误吞掉或误报为成功；它准确披露了内部测试缝的现有契约。

### 最终状态

**VERIFIED_FIXED**。
