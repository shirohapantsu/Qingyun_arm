## 1. 总体结论

**架构适合本期草莓 demo，但当前文档不宜作为“全部冻结、可直接派发”的完整规格。** 可以推进 P0 契约迁移，以及边界清楚的离线业务测试；P1/P3/P4/P5 需要先修订关键问题，真机启动还需独立解决驱动初始化与实测证据链。

## 2. 编码前应修正的问题

### R01｜高：处理决定没有同步，当前存在两套相反的执行规格

证据：初审 §7.1–7.4 已记录取消 main CLI、独立 mock 入口、模板改名、预检前移、D14 封顶失败退出；实施文档 README 首行仍声明 D01–D13 全部冻结，P1 §4/§6.2 和 P5 §2/§3 仍要求 CLI/mock_runtime 与封顶恢复后正常完成。

这是可执行行为冲突，不只是历史说明过时。尤其 D14 涉及失败后是否继续搬臂、是否回 WAITING，不能交给编码者靠文档优先级猜测。

建议一次性同步决定表、主流程伪代码、恢复矩阵、测试预期和验收命令；旧段落直接改成最终规则，历史理由保留在决策记录。独立入口确定后，固定生产配置来源，例如相对项目根定位 `configs/app.local.json`，避免取消 CLI 后配置入口悬空。

D14 的精确触发条件应写成“本次失败后 ignore 达到本次返回目标的 valid_count”。视觉另有新扫描数量变化导致的 `NoTarget(skip_exhausted)`；两者不可都笼统写成“ignore 封顶”。保留原 NoTarget 规则时，要如实说明它不证明每个物理目标都已尝试。

### R02｜高：P3 把基座高度当成相机深度，尺寸/yaw 换算也缺少透视处理

证据：P3 §6 第 3 步（第 92–97 行）先把 `z_top` 定义为 base 系高度，随后要求“OBB 中心像素用 z_top 深度 deproject”。二者虽都以米计量，却不是同一个坐标量。相机离桌距离与物体离桌高度通常相差很大，不能互换。

同节的“像素边长 × Z / f”和图像长轴角直接转 base，仅在额外几何条件下可作近似。文档只要求固定安装，没有约束光轴垂直桌面；相机倾斜时，图像 OBB 长轴也不等同于物体水平长轴。以局部投影为例，相机倾斜 45° 时，基座平面 45° 的轴可投影成约 35.26°，已经超过 5° 验收预算。

建议明确 `Z_rgb`、`z_base` 与高度 `h` 三种量；对齐深度应定义为 RGB 相机系的 Z，并处理投影重叠、无效像素和畸变。中心使用相机深度反投影后变换到 base；若使用已估计的水平面，则做像素射线与该平面求交。长宽/yaw 从 base XY 中的轮廓、点云或经验证的平面映射估计，不把像素尺寸直接视为真实水平尺寸。

离线验收至少加入：倾斜相机、非零外参平移、fx≠fy、画面边缘和非零畸变。参考值应由独立正向投影生成，避免测试复写错误公式。透视模型和坐标方向参考 [OpenCV 官方 PnP 文档](https://docs.opencv.org/4.12.0/d5/d1f/calib3d_solvePnP.html)。

### R03｜高：main 冷启动漏掉 `cloud_model.init(cfg)`

证据：P1 §4（第 195–199 行）只初始化 asr 和 vision，之后宣布 ready；P2 §2（第 33–34 行）明确业务函数在 init 前调用必须抛 HardError。P1 §5 随后直接调用 `cloud_model.select_plan(text)`。

照规格实现时，第一条非空转写就会触发 LLMHardError，无法进入任务。

建议在 ready 前显式调用一次 `cloud_model.init(cfg)`，并定义 `LLM_INIT_FAILED`。初始化测试应验证三个模块全部成功初始化后才能 ready，首次有效口令可以进入 Plan。独立 mock 入口按既有决定跳过真实云初始化。

### R04｜高：独立 mock 入口仍需补齐时钟与场景装配契约

证据：P1 §4 使用 `ArmController(motor, params)`；`tests/mock_motor.py::SimTime` 默认从 1000 秒起步，而 ArmController 默认用真实 `time.monotonic/monotonic_ns/sleep`。本次直接构造验证：第一次 `arm.executor.read_feedback()` 报反馈过期；向两者注入同一 SimTime 后读取通过。

因此初审“ArmController 的时钟有默认值，可直接构造”只适用于真实时钟路径，不能推广到既有 MockMotor。

独立入口至少应明确：

```python
sim_time = SimTime()
motor = MockMotorController(params, sim_time)
arm = ArmController(
    motor, params,
    clock=sim_time.monotonic,
    sleep=sim_time.sleep,
    clock_ns=sim_time.monotonic_ns,
)
```

同时给出仿真 K、places 和接触物体/失败序列的来源，不能依赖 P4 尚未产生的真实 K；复用真实 Plan 和运动代码，避免独立入口复制另一套业务循环。回放帧应随成功/失败提供相符的后续场景；第二个任务必须明确如何获得新帧序列，不能用永久回放耗尽来“通过”连续任务测试。

### R05｜中：请求总时限尚未被技术方案保证

证据：P2 §3.1 要求连接加请求总时限，§4 却只写“客户端超时=total_timeout_s”。若采用 HTTPX，客户端 timeout 分别约束 connect/read/write/pool，read 是等待下一块数据的时限，不自动等于整个调用的墙钟上限。参见 [HTTPX 官方超时说明](https://www.python-httpx.org/advanced/timeouts/)。

建议区分连接/读写超时与端到端 deadline，选择能中止同步请求的实现，并明确 LLM 两次语义请求是各自计时还是共享预算。测试加入持续缓慢返回数据的服务替身；只用“立即返回超时异常”的 stub 不能证明总时限成立。

## 3. 真机验收前必须补齐的条件

### R06｜高：不测目标高度时，不能宣称运动碰撞检查会为超高物体兜底

证据：D10（实施文档 README 第 147 行）把第三维上界交给单层摆桌及运动碰撞检查；P3 不输出高度，P0 明确运动仅消费 position/yaw。`arm_control.py::_target_obb/held_obb`（第 541、572 行附近）始终使用固定 `params.grasp.object_envelope_m` 建模，`safety.py::object_box` 也没有真实高度输入。

因此实际物体超过固定包络时，运动侧未必能发现，不能保证返回 COLLISION。单层只排除叠放，不能证明一颗果实不超高。当前真实 envelope 为 `[0.07, 0.045, 0.045] m`；按方案半高模型，一颗高 50mm 的果实中心 Z 约为 22.60mm，仍落在当前允许的 20–28mm 中心高度区间内，位置过滤也不能保证拦截超高物体。

维持“不新增高度过滤”的既有决定时，建议把 demo 样本实际高度不超过 45mm、长宽及测量误差满足包络作为量具抽检/样本准入条件，保留记录；删去“超高必由运动兜底”的暗示。以后若需处理任意果实，再讨论扩展感知与过滤。P3 “近似余量由运动误差包络吸收”也应给出尺寸测量误差依据：现有膨胀项包含位置、yaw、工具、闭合位移和扫掠误差，未单列尺寸低估误差。

### R07｜高：预检前移解决不了力矩使能时的旧目标问题

证据：`motor_control.py` 第 1490–1537 行的默认初始化进行应答/身份核验后直接 `configure_torque(True)`；第 1557–1576 行逐轴使能，没有先核对旧 Goal_Position 与当前反馈。完整落地方案 §4.1 已要求检查旧目标不一致及部分使能失败，但 P1 只保留了默认构造。

仓库 `scripts/validate_home_waypoint_motion.py` 已有专用的目标预置、六轴力矩读回与使能前后位移核对；这些步骤还包含 CAL-052 对 Goal_Position 写入会隐式上力的处理，不能把一般“先预写目标再使能”当作无动作步骤照搬。

建议把经过本机验证的启动握手整理为驱动公开生命周期接口，明确旧目标不一致、部分使能、读回中断时的状态和处置。用假总线检验顺序，再独立验证真机行为。main 不访问驱动私有状态；运行期 terminate 保持原有不追加命令的规则。此项是已有启动要求的落实，不能由“调用了 initialize”直接判定完成。

### R08｜高：P4 的真实抓取统计入口没有交付，发布闭环仍有缺口

证据：P4 §2.7/§3 要求先完成至少 30 次真实抓取试验，再 promote；生产 main 只接受 verified。既有 `scripts/calibrate.py::_capture_hardware` 第 554–558 行明确拒绝 timing/motion/grasp/pick_place，要求从运行期日志导入。现有 `validate_home_waypoint_motion.py` 提供 draft 期间的专用空载路线验证，但不是完整抓放统计工具。

因此“标定期允许采集”尚不足以说明首次 verified 所需的完整抓放证据如何产生。

建议 P4 明确新增或扩展专用抓放验收入口：基于 draft 标定候选执行经审查的动作范围，保留真实 profile、资源哈希、运行状态、逐次成功/掉落/损伤及操作者记录，导出既有 validate 接受的格式。生产加载器仍拒绝 draft，真实记录不能被标成 simulation。先验收入口与数据链，再进行真实样本试验。

### R09｜中高：近圆样本退出 yaw 验收，不等于获得运行许可

初审 §7.2 决定“不改视觉管线，近圆不参与 5° yaw 验收”。该决定能解决退化长轴难以定义的问题，但不能证明运行期的误差包络与抓取方向仍成立。

证据：`safety.py::build_error_envelope` 第 250 行用 profile 的 5° yaw 上界计算物体外缘膨胀；姿态文档 §2 说明单动指夹爪的相反方向接触几何可能不同。近圆形目标仍被下发时，还可能引发姿态跳变、不可达或接触侧变化。

建议在不改视觉管线的范围内，先把近圆样本排除出本期允许抓取的 demo 样本集合，并冻结圆度判据及数据来源。若需要运行期接受近圆果，则另行验证所选方向、包络与接触行为；不能只从误差统计中删掉它们。这里不擅自指定新的圆度阈值。

### R10｜中：标定采样方法与验收统计口径还不够具体

P4 §2.2 同时要求“至少四个非共面点”和“触碰标定板角点”；单块平板角点共面。若观测的是指尖标记，标记与 TCP 也必须是同一点，或有明确的刚性偏移变换。PnP 输出通常为 world/base 到 camera 的变换，保存 `T_base_camera` 时须取逆。求解器与最少点数应匹配；例如 OpenCV 默认迭代法的非共面初始化要求至少六点，而四点可采用相应 PnP 方法。参见 [OpenCV 官方说明](https://docs.opencv.org/4.12.0/d5/d1f/calib3d_solvePnP.html)。

建议明确选择平面标定板法或跨高度三维点法，写出输入点所属坐标系、标记偏移、求解器与输出变换方向；合成测试覆盖非零旋转和平移及矩阵取反错误。

CAL-040/041 还需冻结：位置使用三维欧氏误差；yaw 使用模 180° 最小角差；4mm/5° 是逐样本上限还是其他统计量（既作为运行期误差上界，不能只验均值）；验证样本与视觉检出的一一对应；未检出/被过滤的样本也要记分母。不能只统计 `get_target(0)` 成功返回的样本。TCP 同时用于拟合和真值测量时，即使数据集分开也可能共享系统偏差，应记录参考测量的不确定度，并用独立量具/已知尺寸目标交叉验证。

## 4. 对初审报告的专项更正

### L5 的限制理由不成立

`configs/motion_params.py` 第 247 行定义 envelope 为物体“长、宽、高”；`safety.py::object_box` 按物体 yaw 旋转该盒。它不是固定 TCP 坐标系下的两轴开口限制。

若真实物体长宽被包络包含，即 `L ≤ E_L` 且 `W ≤ E_W`，则任意偏角 β 都有：

```text
|cos β| L + |sin β| W ≤ |cos β| E_L + |sin β| E_W
```

因此逐轴包含足以保证闭合方向投影不超过“同一偏角下的包络投影”，不要求 β 为 0°/90°。逐轴包含和单个投影约束本来也不是完全等价的条件；初审混淆了“等价”与“保守充分条件”。

现有 `scripts/calibrate.py::_derive_preopen_pct`（第 2157 行起）按 envelope、yaw_offset 及 yaw 误差带计算预张；闭合投影函数位于运动学工具模块，但持物碰撞盒的构造逻辑不同，不能混为一谈。

本次实算：40×20mm 物体位于 50×40mm 包络内，β=45° 时投影分别为约 42.43mm、63.64mm；扫描 -180° 至 180° 共 361 个整数角没有包含违例。

**建议纠正初审的数学依据。** 初审第七章已记录增加 `{0,90}` 断言的决定，本次不擅自撤销；若保留，只应说明它是本期已标定姿态范围的产品限制。实际需要保证的是：长宽轴语义一致、预张开口覆盖包络及误差、修改 yaw_offset 后重新派生相关参数并验证。
