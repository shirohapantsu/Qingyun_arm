# servo_params.py 总结

> 青云机械臂抓取子系统 · 电机侧（C/3 号）真值配置中心：总线参数 + 舵机标定模型 + 换算因子
---

## 一、一句话定位

`servo_params.py` 是整条电机链路的**唯一真值来源**：所有"需要拍板定死"的数值——总线怎么连、刻度怎么换算、6 个关节分别是谁、能转到哪——全部集中在这一个文件里。`motor_control.py` 的逻辑**不写死任何魔法数字**，需要什么就从这里读。

它是"软件逻辑"和"这台具体机器人硬件"之间的**唯一接线板**：换舵机、改限位、回填标定，只动这一个文件，其余代码零改动。

---

## 二、它掌握的四种"真值"

| 类别 | 内容 | 谁在用 |
|---|---|---|
| **总线参数** | 串口 `SERVO_PORT`（默认 `/dev/ttyACM0`，环境变量 `QINGYUN_SERVO_PORT` 可覆盖）、波特率 1M、超时 50ms、重试 2 次、应答探测窗口 8ms | `motor_control.py` 创建 `FeetechBus` 时逐个传入 |
| **换算因子** | 位置 1 步 = 360/4096°、速度单位 = 步/s、电流 1 bit = 6.5mA | `get_feedback`：把舵机原始读数变成 度 / 度每秒 / mA |
| **标定模型** | `ServoJointConfig`（name / servo_id / 软限位 / zero_raw / direction / offset_deg）+ 互逆公式 `deg_to_raw` / `raw_to_deg` + 6 关节实例 `MOTOR_CONFIGS` | `send_action`（关节角→raw 写入）、`get_feedback`（raw→关节角回传）、软限位钳位 |
| **布局常量** | 夹爪百分比端点 `GRIPPER_DEG_AT_0/100_PCT`；反馈整块读 `FEEDBACK_START_ADDR=0x38`、`FEEDBACK_LEN=15` 及 15 字节内部偏移表 | `send_action`（夹爪换算）、`_read_raw_state`（拆包 6 项状态） |

"当前角度在地址 0x38、1 步 0.08789°"这类**硬件知识**在这里写一次、带好出处；上层永远只调用 `cfg.raw_to_deg(...)` 这种**有意义的函数**，不直接碰换算。

---

## 三、它替大家兜住的六件事

1. **角度换算只此一份**：`raw ↔ deg` 公式全项目唯一实现（且在 `ServoJointConfig` 里互为逆运算），杜绝"每处各写一遍、符号方向不一致"的经典 bug。
2. **软限位的唯一数据源**：`min_deg / max_deg` 同时供给 `send_action` 的最后一道钳位闸和 `sweep_joint` 扫掠自检——两处读同一个真值，永远不会"闸门和检查用的不是一套限位"。
3. **单位换算有据可查**：每个因子都带来源注释（数据手册 Excel、官网评测、lerobot tables.py、commanderfun 交叉核对），将来怀疑数值错了，知道去哪查。
4. **环境差异被吸收**：串口默认值 + 环境变量覆盖——真机（香橙派 Linux）和开发机（Windows COM 口）切换零代码改动。
5. **"还没标定"是显性的**：`zero_raw=2048 / direction=1 / offset_deg=0` 三个带 **标定 TODO** 的假定值写进默认参数——项目不会把"软件跑通了"误当成"标定好了"；标定完成只需回填 3 个数。
6. **变更影响面被压到最小**：改舵机 ID 烧录顺序、改关节量程、回填标定值——**只改数据文件，逻辑代码零改动**（这是它与 Lerobot"查表驱动"同思路的体现）。

---

## 四、它在项目里的位置

```
main.py（总开关：真机 / Mock）
  └─ arm_control.py（B 侧上层：按 MotorController 契约编程，不看实现）
        └─ motor_control.py（C 侧实现：STS3215MotorController）
            ├─ 读本文件的所有真值 ← servo_params.py（本文件：纯数据 + 纯函数）
            │     契约形状来自 common_interface.py（方法签名 / JointFeedback）
            └─ 调 feetech_bus.py（帧级收发，只认 ID + 寄存器 + 字节）
                  └─ pyserial → USB2Serial → 6 台 STS3215 总线
```

数据流一句话：**上层要角度(deg) → motor_control 用本文件的公式换算 → feetech_bus 写原始值(0..4095)**；回传方向正好相反。本文件就是这条链上"两套单位制"的翻译官。

---

## 五、它刻意不做什么

- **不含任何通信知识**：不认识帧头、校验和、寄存器地址表（那是 `feetech_bus.py` 的 `REG_*`）；
- **不含接口契约**：方法签名、返回结构体形状在 `common_interface.py`——本文件只提供"数值"，不定义"约定"；
- **不含流程与决策**：没有 if/else 判断、不懂抓取流程、不调度时序，只有数据 + 两个纯换算函数；
- **不执行任何硬件操作**：import 它不会打开串口、不会连舵机，可安全地在任何环境（包括 Mock 测试）加载；
- **不替代标定**：它只负责把标定结果存下来并用起来，标定动作本身（手动掰零位、测量）在别处做。

**为什么能这么干净？** 因为它遵循"数据与逻辑分离"：文件里只有**事实**（这台机器人长什么样），没有**行为**（怎么用它）。事实越集中、越单一，逻辑代码就越不需要知道硬件细节——这是它与 `feetech_bus.py`"薄而快"一脉相承的设计取向：**配置集中给一处，其余代码只认语义（名字、角度），不认物理（地址、刻度）。**

---

## 六、对"抓取应用"最实际的三个收益

1. **标定 = 填 3 个数字**：真机零位/方向标定完成后，回填 `zero_raw / direction / offset_deg` 即全部生效——`get_feedback` 的角度、`send_action` 的限位、扫掠自检的判断自动全部对齐，不需要改任何一行逻辑。
2. **一处改量程，全链路安全同步生效**：`send_action` 的最后一道软限位钳位和 `sweep_joint` 的扫掠边界读的是同一份 `MOTOR_CONFIGS`——不存在"改了 A 处忘了 B 处"导致的越程风险。
3. **预算写在注释里，性能心里有底**：超时 50ms、6 次块读 ≈15ms、30Hz 节拍 33ms 的余量分析直接写在参数旁边——将来换同步读优化、或发现时序告急时，对照注释就知道瓶颈在哪、余量在哪。

---

## 七、一句话总结

> 在项目看来，这个文件 = **"这台机器人长什么样"的唯一答案**：不做事、不做决定，只负责把所有该拍板的真值（端口、刻度、关节、限位、标定）集中钉在一处，并配上唯一合法的换算公式。
